# レビュー

作業の注意点と制約．読むのはレビュー担当（`reviewer` エージェント）で，作業する担当は読まない．レビュー担当は [workflow.md](workflow.md)（手順）と [conventions.md](conventions.md)（書き方）も読み，作業がそれらとこの文書に合っているかを確かめる．この 2 つにあることは，ここに重ねて書かない．本ごとの事情は本のリポジトリの `docs/book.md` に，本ごとの注意点と制約は（あれば）`docs/book-review.md` にあり，食い違うときはそちらに従う．

## レビューのしかた

- 依頼文からレビューの種類（校正，原書の誤りの修正，証明の簡略化・補完，担当ブランチの最終検証）と範囲を読み取る．校正のほかは「どの作業にも当てはまること」も確かめる．
- ソース，`corrections/`，git の差分，原書だけを見る．依頼文やコミットメッセージに担当の説明があっても根拠にしない．
- 依頼文に規約にない書き方の方針（どう書くかの選択）があれば，それは正しさについての説明や結論ではないので，前提として読む．その方針それ自体は指摘しないが，それで論理が壊れていれば指摘する．方針が conventions.md や `docs/book.md` と食い違うときは「体裁」として指摘する．
- md の「修正しなかった点・メモ」に，反映しなかった指摘とその理由があれば読む．理由が成り立っていれば同じ指摘を繰り返さず，成り立たないときはそのことを指摘する．
- リポジトリのファイルは編集しない．画像の切り抜きなどの一時ファイルは，リポジトリの外に置く．
- 校正のほかは `make check` を実行し，NG と「要確認」（警告）をすべて見る．
- 指摘は「誤り」（反例か理由を書く）「隙間」「体裁」（conventions.md と合わない所を含む）に分け，場所（ファイルと行，ID，原書のページ）とよりどころを書く．指摘がなければ，確かめた範囲とともにそう書く．

## どの作業にも当てはまること

workflow.md と conventions.md のとおりかに加えて，次を確かめる．

- 変更が workflow.md の「並列作業」の変えてよいファイルに収まっている．忠実版は「忠実版を直す」のときだけ変わっている．
- 忠実版は原書と完全に一致する（誤植もそのまま）．書き起こしの誤りを修正版で直していない．
- 本の記号のマクロにすでにあるマクロは，必ずそれを使っている．
- 原書の番号を残す式に `equation` と `\tag` を使っていない（hyperref のアンカー名が重複する）．
- 原書を直した箇所には漏れなく `\fixat{ID}` がある．「要確認」の変更を一つずつ見て，ID なしの修正や修正版での書き起こしの直しでないか確かめる．
- 種類に「補完」「注記」「簡略化」「書き換え」を含む修正には，短いものにも漏れなく印がある．印の中に印がない．
- `\origpage` が数式や脚注の中，見出しの直前（空行ができる），定理環境の直後（見出しが前のページに取り残される）にない．
- 「記述（補完）」「記述・証明（補完）」で足した定義・事実（「証明（簡略化）」のまま足したものも）が正しく，証明を付けていない部分は標準的な事実の範囲にある．
- 足した定義・事実は，単独で読んで自然な形で述べてあり，使う場面に合わせて仮定を曲げていない（当てはめは使う側で調整してある）．
- 足した定義と命題が分かれていて，仮定の違う事実は別の命題になっている（「2) の状況で」のように前の項の状況を引き継いでいない）．
- 足した命題の主張が，証明が引く単位で番号付きの項に分かれている（「2) の後半」のような引き方がない）．
- 足した定義・事実を含む修正の種類が，conventions.md の種類の表に合っている．
- 修正版で補った文の用語が本の既存の語にそろっていて，本にあるものを別の語で呼んでいない．
- 修正版で補った文で主張の中の番号付きの項（「1)」「(a)」など）を引くとき，近くで別の定理・定義も引いていれば，「定義 1.2.3 の 1)」のようにどの定理・定義の項かが書いてある．
- 原書の誤りが md のメモだけに残っていない（「偽」「成り立たない」「穴」などを含む ID のないメモは「要確認」に出る）．

## 校正

原書の画像と忠実版のソースだけを見て照合する．

- 各ページの画像を実際に見て 1 行ずつ比べる．細かい添字，プライム，チルダ・バー・ハットの区別，取り違えやすい文字（$d_X$ と $d_Y$，$\mu$ と $\nu$，$x$ と $y$）は，画像を切り抜いて拡大して読む．
- 報告するのは，文字・記号・添字・句読点の誤りや脱落，`\term` の過不足，番号の違い，原書の明らかな数学の誤り（修正版で直す候補として）．改行，ページ割り，空きなどのレイアウトの違いは無視する．
- 指摘には，原書のページ，ソースの行番号，原書の表記，ソースの表記を書く．

## 原書の誤りの修正

- 主張・式・定義が成り立たない，または証明に原書が明示していない穴があるときは，修正版の本文に必ず反映する．**直すのが基本**で，直したものは次を満たす．
  - 反例があるか，誤りである理由がはっきりしている．
  - 正しい形が一つに決まる（標準的な形，または仮定の最小限の追加・結論の最小限の弱め）．文献で確かめられるなら確かめてある．
  - その主張や式を使っている箇所（他の章も）の議論が，直した形でも通り，それらも同じ ID で直してある．
  - より小さな直し方がない．
- 注記にしてよいのは，正しい形の候補が複数あって決められないときと，本書の範囲を超える結果が要るときだけ．本当に直せないかも確かめる．
- 原書の主張や注意そのものの誤りは，証明の補完ではなく誤りとして直す．
- 「記述（簡略化）」は本当に同値で，明らかに簡潔になっている．「主張（補完）」の強めた分の証明が正しい．どちらも，その記述を使っている箇所（他の章や補完の中も）がそろえて直してある．

## 証明の簡略化・補完

- 対象の選び方が workflow.md の「証明の簡略化・補完」の 1 に合っている．
- 短くなっても情報が減るもの（陽な定数や評価が消える，具体的な構成が抽象的な存在に置き換わるなど）は置き換えない．前方参照，背理法への切り替え，抽象的な結果への帰着はよい．短くなっても追いにくくなったものは差し戻す．
- 最後に出た定数に合わせて最初の $\varepsilon$ などを取り直す書き方（「最初に $\varepsilon/3$ をとっておけば」）を，最初に決めておく形（「$\delta = \varepsilon/3$ とおく」）に書き換えない．
- 新しい証明を 1 行ずつ確かめる．不等号の向き，定数の依存性，部分列のとり方，極限の順序，測度の有限性や可測性の仮定は特に見る．参照先の主張も実際に読み，引用が循環していないか，使った事実が本書か標準的な事実の範囲にあって「前提にした事実」に書いてあるかを確かめる．
- 理由を書く粒度が本の水準に合っている．原書が飛ばした所でも 1 行で出る推論には理由は要らず，1 行で出ない中間式や不等式には理由がある．
- 段落の書き出しが同じ形（「〇〇である．実際，…」など）ばかり続いていない．
- ステップに分けた証明に，見出しと重なる方針の一文や，ステップの中で方針だけを述べる段落がない．
- 事実をまとめて引いたせいで（「A と B と定理 1.2.2 から」など）何を何に当てはめたかが見えない所がない．あれば，当てはめ（どの対象が定理のどの仮定を満たすか）を書くか，その型の事実を命題にまとめて本文には仮定の確認だけを残すよう指摘する．
- 標準的な事実を「標準的な判定法から」「〇〇の計算から」とだけ書いて，何を使ったかが分からない所がない．
- 段落が依存の順に並んでいる．前の段落の結論を使う段落は，なるべくその直後にあり，間に別の段落が入るときはどこで示した結論かが書いてある（直前の無関係な段落から出たように読める並びがない）．
- 補完の途中で直した原書の誤りと，その章でそれまでに入れた修正のうち「論理」のものと数式の修正も，「原書の誤りの修正」の観点で確かめる．

## 担当ブランチの最終検証

- 担当ブランチは，`git fetch origin <ブランチ>` の後，`git worktree add --detach <リポジトリの外の一時ディレクトリ> FETCH_HEAD` で取り出して検査し，終わったら `git worktree remove` で消す（依頼した側の作業ツリーは変えない）．変更の範囲は `git diff main...FETCH_HEAD` で見る．
- 変更の範囲，`make` と `make check`，新しい証明の正しさ，対象の選び方を確かめる．
- 依頼した側は差分を読まずに結論だけを受け取るので，結論を短く書く．
